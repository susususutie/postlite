# TDD 代码修改

## 概述

使用测试驱动开发（TDD）流程修改代码，通过"测试先行、循环修复、质量门禁"的方式，确保代码质量和可维护性。

## 适用场景

- UI/样式修复
- 功能增强
- Bug 修复
- 组件重构
- 依赖升级

## 前置条件

- 项目已配置测试框架（Vitest/Jest等）
- 项目已配置代码检查工具（ESLint等）
- 了解项目使用的包管理器（npm/pnpm/yarn/bun）

## 变量定义

| 变量名 | 说明 | 检测方式 |
|--------|------|----------|
| `{package_manager}` | 包管理器命令 | 检查 `packageManager` in package.json 或 lock 文件 |
| `{test_file}` | 测试文件路径 | 根据修改的文件确定 |
| `{source_file}` | 源文件路径 | 用户指定或代码分析确定 |

## 执行流程

### 阶段 1：问题归因

#### 1.1 深入理解问题
```
用户反馈 → 代码探究 → 根本原因分析 → 确定修复位置
```

**关键动作**：
- 读取相关源码文件
- 分析组件结构
- 探究第三方库行为（如有必要，查看 node_modules 源码或官方文档）
- 确认问题根因（不是表象，而是根本原因）

**输出**：
- 问题根因说明
- 建议的修复方案（1-3个）
- 每个方案的优缺点

#### 1.2 方案确认
与用户确认：
- [ ] 修复方案选择
- [ ] 是否只修改特定区域（如"只改右侧面板"）
- [ ] 样式值处理方式（CSS变量/硬编码/其他）

### 阶段 2：测试先行

#### 2.1 编写测试

**测试文件命名**：`[Component].test.tsx` 或 `[feature].test.ts`

**测试内容要求**：
1. **功能验证测试** - 验证修改是否正确应用
2. **回归测试** - 确保不会破坏现有功能
3. **边界测试** - 验证边界条件

**测试原则**：
- 测试验证的是**结果**而非**实现方式**
- 避免测试内部实现细节（如具体函数调用）
- 优先使用用户可见的行为进行验证

**示例结构**：
```typescript
describe('Component - Feature', () => {
  // 测试1：修复必须存在
  it('should have fix applied', () => {
    // 读取源码验证修改存在
  });

  // 测试2：配置正确
  it('should have correct configuration', () => {
    // 验证配置项
  });

  // 测试3：无硬编码值（如需要）
  it('should not use hardcoded values', () => {
    // 验证使用变量/主题token
  });
});
```

#### 2.2 运行测试（预期失败）

```bash
{package_manager} run test:run -- {test_file}
```

**验证点**：
- [ ] 测试执行无环境错误
- [ ] 测试因预期条件不满足而失败
- [ ] 失败信息清晰明确

**失败处理**：
- 如测试环境错误（缺少 mock/setup），先修复测试配置
- 确保测试失败是因为条件不满足，而非代码错误

### 阶段 3：循环修复

#### 3.1 修复策略

```
方案1（最优先）→ 最多3次尝试 → 不成功
  ↓
方案2（备选）→ 最多3次尝试 → 不成功
  ↓
方案3（兜底）→ 最多3次尝试 → 不成功
  ↓
报告失败，请求用户介入
```

**方案选择优先级**：
1. **官方 API** - 使用第三方库提供的配置属性（如 `zeroWidthTriggerStyle`）
2. **CSS 覆盖** - 添加 CSS 类覆盖默认样式
3. **自定义组件** - 使用自定义组件替换默认实现

#### 3.2 子 agent 修复任务

**任务要求**：
- 明确指定修改文件路径
- 提供具体代码修改示例
- 强调约束条件（如"只修改右侧面板"）
- 要求使用特定方案

**反馈循环**：
```
子 agent 修改代码 → 运行测试 → 向用户汇报结果
     ↑                                    ↓
     └──────── 失败则调整重试（最多3次） ←─┘
```

#### 3.3 运行测试（验证修复）

```bash
{package_manager} run test:run -- {test_file}
```

**验证点**：
- [ ] 所有新测试通过
- [ ] 无意外失败

**结果处理**：
- **通过**：进入阶段 4
- **失败**：根据错误信息调整，重试（同一方案最多3次）

### 阶段 4：质量门禁

#### 4.1 代码检查

```bash
{package_manager} run lint
```

**处理**：
- 如有错误，修复后再继续
- 常见：未使用变量、格式问题
- 尝试自动修复：`{package_manager} run lint -- --fix`

#### 4.2 回归测试

```bash
{package_manager} run test:run
```

**验证点**：
- [ ] 所有现有测试仍通过
- [ ] 无新失败
- [ ] 覆盖率不下降（如适用）

**失败处理**：
- 如有测试失败，分析影响范围
- 修复或询问用户是否接受

## 工具命令速查

```bash
# 运行特定测试文件
{package_manager} run test:run -- [file]

# 运行所有测试
{package_manager} run test:run

# 代码检查
{package_manager} run lint

# 自动修复 lint 错误
{package_manager} run lint -- --fix
```

## 完整示例：UI 样式修复

```
用户：右侧面板 trigger 按钮左边框不明显

阶段 1：问题归因
├── 读取 App.tsx 分析结构
├── 探究 Ant Design Sider 组件源码
├── 发现：reverseArrow 时 trigger 缺少左边框
└── 方案：
    ├── A. 使用 zeroWidthTriggerStyle（推荐）
    ├── B. CSS 覆盖
    └── C. 自定义 trigger

阶段 2：测试先行
├── 编写 App.test.tsx
│   ├── 测试：zeroWidthTriggerStyle 必须存在
│   ├── 测试：样式配置正确
│   └── 测试：无硬编码颜色
├── 运行测试：失败 ✓（符合预期）
└── 确认测试环境正常

阶段 3：循环修复
├── 尝试方案A（zeroWidthTriggerStyle）
│   ├── 第1次：子 agent 修改代码
│   ├── 运行测试：通过 ✓
│   └── 成功，无需后续方案
└── （如失败则尝试方案B、C，各最多3次）

阶段 4：质量门禁
├── {package_manager} run lint：通过 ✓
├── {package_manager} run test:run：418 passed ✓
└── 完成

输出：
- 修改的文件：src/App.tsx
- 测试文件：src/App.test.tsx
- 测试结果：通过
```

## 输入/输出

### 输入

| 名称 | 类型 | 必需 | 说明 |
|------|------|------|------|
| 问题描述 | string | 是 | 用户反馈的问题或需求 |
| 源文件路径 | string | 否 | 需要修改的文件（如未提供则自动检测） |
| 约束条件 | string[] | 否 | 修改限制（如"只修改右侧面板"） |
| 偏好方案 | string | 否 | 用户指定的实现方案 |

### 输出

| 名称 | 类型 | 说明 |
|------|------|------|
| 修改的文件 | string[] | 所有被修改的文件路径列表 |
| 测试文件 | string | 新增的测试文件路径 |
| 测试结果 | boolean | 测试是否通过 |
| lint 结果 | boolean | 代码检查是否通过 |

## 注意事项

### 1. 包管理器检测
- 优先检查 `package.json` 中的 `packageManager` 字段
- 其次检查 lock 文件（`pnpm-lock.yaml`/`package-lock.json`/`yarn.lock`）
- 默认使用 `npm`

### 2. 测试编写原则
- 测试验证的是**结果**而非**实现方式**
- 避免测试内部实现细节（如具体函数调用）
- 优先使用用户可见的行为进行验证

### 3. 修复策略优先级
- **优先**：官方 API（如 `zeroWidthTriggerStyle`）
- **其次**：CSS 覆盖
- **最后**：自定义组件

### 4. 循环终止条件
- 某方案测试通过 → 终止循环
- 某方案尝试3次均失败 → 切换到下一方案
- 所有方案均失败 → 报告用户，请求介入

## 失败处理

| 场景 | 处理方式 |
|------|----------|
| 测试环境错误 | 检查 `test/setup.ts` 或等效文件，补充必要的 mock |
| 三次尝试均失败 | 报告失败原因，请求用户介入或调整方案 |
| Lint 无法自动修复 | 手动修复或询问用户是否跳过 |
| 测试通过但功能异常 | 增加端到端测试或手动验证步骤 |
| 回归测试失败 | 分析影响范围，修复或询问用户 |
