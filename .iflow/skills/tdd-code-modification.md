# TDD 代码修改

## 概述

使用测试驱动开发（TDD）流程修改代码，通过"测试先行、循环修复、质量门禁"的方式，确保代码质量和可维护性。

## 适用场景

- UI/样式修复
- 功能增强
- Bug 修复
- 组件重构
- 依赖升级

## 前置条件

- 项目已配置测试框架（Vitest/Jest等）
- 项目已配置代码检查工具（ESLint等）
- 了解项目使用的包管理器（npm/pnpm/yarn/bun）

## 变量定义

| 变量名 | 说明 | 检测方式 |
|--------|------|----------|
| `{package_manager}` | 包管理器命令 | 检查 `packageManager` in package.json 或 lock 文件 |
| `{test_file}` | 测试文件路径 | 根据修改的文件确定 |
| `{source_file}` | 源文件路径 | 用户指定或代码分析确定 |

## 执行流程

### 阶段 1：问题分析与方案设计

#### 1.1 深入理解问题
```
用户反馈 → 代码探究 → 根本原因分析 → 确定修复位置
```

**关键动作**：
- 读取相关源码文件
- 分析组件结构
- 探究第三方库行为（如有必要）
- 确认问题根因

**输出**：
- 问题根因说明
- 建议的修复方案（1-3个）
- 每个方案的优缺点

#### 1.2 方案确认
与用户确认：
- [ ] 修复方案选择
- [ ] 是否只修改特定区域（如"只改右侧面板"）
- [ ] 样式值处理方式（CSS变量/硬编码/其他）

### 阶段 2：TDD 实施

#### 2.1 编写测试

**测试文件命名**：`[Component].test.tsx` 或 `[feature].test.ts`

**测试内容要求**：
1. **功能验证测试** - 验证修改是否正确应用
2. **回归测试** - 确保不会破坏现有功能
3. **边界测试** - 验证边界条件

**示例结构**：
```typescript
describe('Component - Feature', () => {
  // 测试1：修复必须存在
  it('should have fix applied', () => {
    // 读取源码验证修改存在
  });

  // 测试2：配置正确
  it('should have correct configuration', () => {
    // 验证配置项
  });

  // 测试3：无硬编码值（如需要）
  it('should not use hardcoded values', () => {
    // 验证使用变量/主题token
  });
});
```

#### 2.2 运行测试（预期失败）

```bash
{package_manager} run test:run -- [test-file]
```

**验证点**：
- [ ] 测试执行无环境错误
- [ ] 测试因预期条件不满足而失败
- [ ] 失败信息清晰明确

#### 2.3 实施修复

**策略**：使用子 agent 循环修复

```
方案1（最优先）→ 最多3次尝试 → 不成功
  ↓
方案2（备选）→ 最多3次尝试 → 不成功
  ↓
方案3（兜底）→ 最多3次尝试 → 不成功
  ↓
报告失败
```

**子 agent 任务要求**：
- 明确指定修改文件路径
- 提供具体代码修改示例
- 强调约束条件（如"只修改右侧面板"）
- 要求使用特定方案（如"使用 zeroWidthTriggerStyle"）

#### 2.4 运行测试（预期通过）

```bash
{package_manager} run test:run -- [test-file]
```

**验证点**：
- [ ] 所有新测试通过
- [ ] 无意外失败

### 阶段 3：质量保证

#### 3.1 代码检查

```bash
{package_manager} run lint
```

**处理**：
- 如有错误，修复后再提交
- 常见：未使用变量、格式问题

#### 3.2 回归测试

```bash
{package_manager} run test:run
```

**验证点**：
- [ ] 所有现有测试仍通过
- [ ] 无新失败
- [ ] 覆盖率不下降（如适用）

### 阶段 4：提交

#### 4.1 准备提交

```bash
git diff [files]      # 查看修改
git add [files]       # 添加文件
git status            # 确认状态
```

#### 4.2 编写提交信息

**格式**：
```
<type>: <简短描述>

- 详细变更1
- 详细变更2
- 详细变更3

<关联信息>
```

**类型**：
- `fix`: Bug 修复
- `feat`: 新功能
- `refactor`: 重构
- `test`: 测试相关
- `style`: 样式修改

#### 4.3 执行提交

```bash
git commit -m "..."
git log --oneline -3  # 验证提交
```

## 关键原则

### 1. 测试先行
- 先写测试，再改代码
- 测试要验证结果，而非实现方式

### 2. 循环修复
- 每个方案最多3次尝试
- 失败后切换到备选方案
- 记录每次尝试的问题

### 3. 质量门禁
- Lint 通过
- 所有测试通过
- 覆盖率不下降

### 4. 原子提交
- 一个功能一个提交
- 提交信息清晰完整

## 常见陷阱与解决

| 问题 | 原因 | 解决 |
|------|------|------|
| 测试环境错误 | 缺少 mock/setup | 检查 test/setup.ts |
| 样式不生效 | CSS 优先级问题 | 检查选择器特异性 |
| 第三方库行为异常 | 版本差异 | 查阅官方文档/源码 |
| 测试通过但功能异常 | 测试覆盖不足 | 增加端到端验证 |

## 工具命令速查

```bash
# 运行特定测试文件
{package_manager} run test:run -- [file]

# 运行所有测试
{package_manager} run test:run

# 代码检查
{package_manager} run lint

# 自动修复 lint 错误
{package_manager} run lint -- --fix

# 查看提交历史
git log --oneline -5

# 查看修改内容
git diff [file]
```

## 示例：UI 样式修复流程

```
1. 用户：按钮颜色不对
   ↓
2. 分析：查看组件代码 → 确认是主题 token 未正确应用
   ↓
3. 设计：方案A-修改组件内联样式，方案B-添加 CSS 类
   ↓
4. 确认：用户选择方案B
   ↓
5. TDD：
   - 编写测试：验证 CSS 类存在且样式正确
   - 运行测试：失败（符合预期）
   - 实施修复：子 agent 添加 CSS 类
   - 运行测试：通过
   ↓
6. 质量：
   - {package_manager} run lint ✓
   - {package_manager} run test:run ✓
   ↓
7. 提交：git commit -m "fix: correct button color..."
```

## 输入/输出

### 输入

| 名称 | 类型 | 必需 | 说明 |
|------|------|------|------|
| 问题描述 | string | 是 | 用户反馈的问题或需求 |
| 源文件路径 | string | 否 | 需要修改的文件（如未提供则自动检测） |
| 约束条件 | string[] | 否 | 修改限制（如"只修改右侧面板"） |
| 偏好方案 | string | 否 | 用户指定的实现方案 |

### 输出

| 名称 | 类型 | 说明 |
|------|------|------|
| 修改的文件 | string[] | 所有被修改的文件路径列表 |
| 测试文件 | string | 新增的测试文件路径 |
| 测试结果 | boolean | 测试是否通过 |
| 提交哈希 | string | git commit 的哈希值 |

## 注意事项

1. **包管理器检测**
   - 优先检查 `package.json` 中的 `packageManager` 字段
   - 其次检查 lock 文件（`pnpm-lock.yaml`/`package-lock.json`/`yarn.lock`）
   - 默认使用 `npm`

2. **测试编写原则**
   - 测试验证的是**结果**而非**实现方式**
   - 避免测试内部实现细节（如具体函数调用）
   - 优先使用用户可见的行为进行验证

3. **修复策略**
   - 优先使用官方 API（如 `zeroWidthTriggerStyle`）
   - 其次使用 CSS 覆盖
   - 最后考虑自定义组件

4. **质量门禁**
   - 任何提交必须通过 lint 检查
   - 任何提交必须通过所有测试
   - 覆盖率不应下降（如项目配置了覆盖率检查）

## 失败处理

| 场景 | 处理方式 |
|------|----------|
| 测试环境错误 | 检查 `test/setup.ts` 或等效文件，补充必要的 mock |
| 三次尝试均失败 | 报告失败原因，请求用户介入或调整方案 |
| Lint 无法自动修复 | 手动修复或询问用户是否跳过 |
| 测试通过但功能异常 | 增加端到端测试或手动验证步骤 |
